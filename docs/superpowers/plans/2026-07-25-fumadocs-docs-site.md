# Fumadocs Documentation Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up a standalone Fumadocs (Next.js) documentation site at `docs-site/` with a fresh, original 11-page step-by-step guide to using DevDeck.

**Architecture:** `docs-site/` is scaffolded via the `create-fumadocs-app` programmatic API (Next.js + `fumadocs-mdx` template, npm), branded with the existing `docs/logo/devdeck.png`, and filled with original MDX content under `docs-site/content/docs/`, ordered by `docs-site/content/docs/meta.json`. It is not wired into the root `Makefile`, `make dev`, or CI — own `package.json`, own `npm run dev`/`npm run build`.

**Tech Stack:** Next.js 16 (Turbopack), `fumadocs-core`/`fumadocs-mdx`/`fumadocs-ui` (installed by the scaffold — exact pinned versions come from whatever `create-fumadocs-app` resolves at scaffold time), React 19, npm.

## Global Constraints

- Node.js 22+ (already a repo-wide prerequisite — see `TUTORIAL.md` §1).
- Package manager: npm (matches the rest of the repo).
- `docs-site/` lives at the repo root, sibling to `frontend/` and `backend/`; it is standalone — no `Makefile` target, no CI wiring, no changes to `TUTORIAL.md`/`README.md`/`COMMANDS.md`/`ARCHITECTURE.md`.
- Logo/favicon source: `docs/logo/devdeck.png` (1254×1254 PNG, already in the repo).
- The installation page sends readers to `https://github.com/ItsMyEyes/devdeck/releases` and documents downloading a prebuilt desktop app or runtime binary. It must **not** contain `git clone`/`make install`/build-from-source instructions.
- Content excludes the Todos, News, and Invoices modules (deferred/unshipped — see `TUTORIAL.md` §9–10) and excludes the MCP issue-tracker server (`TUTORIAL.md` §14) — neither is in the agreed 11-page scope.
- No search backend beyond Fumadocs' built-in local search (ships by default with the scaffold — no extra config needed). No auth-gating.

description: What DevDeck is and what this guide covers.

DevDeck is a multi-project dashboard for coding agents: one operator running
many companies' worth of work from a single pane of glass. It pairs git
worktrees with real terminals, so every branch an agent (or you) touches gets
its own isolated checkout, its own live PTY, and its own tiling workspace of
terminal/editor/file-explorer/git panes.

Under the hood it's a Go backend (SQLite + WebSocket PTYs) and a React
single-page app. You can run it as a single self-contained process on one
machine, or split the "organizational data" and "execution" halves across a
hub and one or more runtime machines — see [Deployment
modes](/docs/deployment-modes).

## What this guide covers

This is a step-by-step walkthrough from installing DevDeck to your first
agent worktree, then a tour of the rest of the app:

1. [Installation](/docs/installation) — get a build running
2. [Your first account](/docs/first-account) — register and (maybe) set up 2FA
3. [Workspaces and projects](/docs/workspaces-and-projects) — organize your work

5. [Working inside a worktree](/docs/working-in-a-worktree) — the tiling pane workspace
6. [Issues](/docs/issues) — the built-in kanban tracker
7. [Agent management](/docs/agent-management) — configure the agent CLIs themselves
8. [Tools](/docs/tools) — document conversion and everyday dev utilities
9. [Deployment modes](/docs/deployment-modes) — hub, runtime, and desktop
10. [Troubleshooting](/docs/troubleshooting)

import { Step, Steps } from 'fumadocs-ui/components/steps';

DevDeck ships as two kinds of downloadable build from the [GitHub Releases
page](https://github.com/ItsMyEyes/devdeck/releases) — pick whichever matches
how you want to run it.

| Build | What it is | Best for |
|---|---|---|
| **Desktop app** | A native app (macOS/Windows/Linux) with the server bundled inside it | Most people — one download, no terminal needed |
| **Runtime/hub binary** | A headless server binary, no UI of its own | Running DevDeck on a remote machine or server |

<Steps>
<Step>

### Open the releases page

Go to [github.com/ItsMyEyes/devdeck/releases](https://github.com/ItsMyEyes/devdeck/releases)
and open the latest release.

</Step>
<Step>

### Download the build for your platform

**Desktop app:**

| Platform | Asset |
|---|---|
| macOS (Apple Silicon) | `devdeck-desktop-macos-aarch64.dmg` |
| Linux (Debian/Ubuntu) | `devdeck-desktop-linux-amd64.deb` |
| Linux (Fedora/RHEL) | `devdeck-desktop-linux-amd64.rpm` |
| Linux (any, portable) | `devdeck-desktop-linux-amd64.AppImage` |
| Windows | `devdeck-desktop-windows-amd64-setup.exe` (or the `.msi`) |

**Runtime/hub binary** (headless): `devdeck-runtime-<platform>` — pick the
asset matching your server's OS/architecture.

</Step>
<Step>

### Run it

- **Desktop app** — install and launch it like any native app. The first
  launch asks how you want to run it; see [Deployment
  modes](/docs/deployment-modes) for what each choice means.
- **Runtime/hub binary** — make it executable and run it with a role flag,
  for example:

  ```bash
  chmod +x devdeck-runtime-*
  ./devdeck-runtime-* --role both --key <any-secret-string> --db devdeck.db
  ```

  See [Deployment modes](/docs/deployment-modes) for what `--role` values
  are available and when to use each.

</Step>
</Steps>

<Callout title="Optional: Tailscale">
  Tailscale is only needed if you're connecting multiple machines together,
  or exposing a hub on your tailnet. A single-machine setup works without it.
</Callout>

Once it's running, open the app (desktop) or its URL in a browser (runtime)
and continue to [Your first account](/docs/first-account).

description: Register, and set up 2FA if it's enabled.

A fresh DevDeck instance has no accounts yet, so you'll land on the login
screen with nowhere to go but **Register**.

## Register

Enter an email and a password (12 characters minimum). What happens next
depends on whether the instance you're connecting to has two-factor
authentication enabled:

- **2FA disabled** — you're logged in immediately, no extra steps.
- **2FA enabled** (the default for hub/runtime builds) — you're sent to a
  **2FA setup** screen:
  1. Scan the QR code with an authenticator app (Google Authenticator,
     Authy, 1Password, …).
  2. Enter the 6-digit code it generates to confirm.
  3. Save the one-time backup codes shown on screen.

<Callout title="Save your backup codes" type="warn">
  You won't see the backup codes again after this screen. They're your only
  recovery path if you lose access to your authenticator app — without them,
  there's no self-service way to recover a locked-out account.
</Callout>

Once 2FA (if any) is set up, logging in from then on is a two-step form:
email/password, then a 6-digit code (or a backup code).

## Where you land

Either way, you land on `/` — which, with no workspace yet, shows an
onboarding screen prompting you to create one. Continue to [Workspaces and
projects](/docs/workspaces-and-projects).

```mdx
---
title: Your first worktree
description: Spawn an agent worktree, or a plain root-mode terminal.
---

From a project's **Worktrees** tab, click spawn to open the new-worktree
dialog.

## Branch mode

The common case — a new isolated branch with an agent (or a plain shell)
attached:

- **Branch name** — a new branch to check out. DevDeck runs a real
  `git worktree add` under `<project>/.wt/<worktree-id>`, so your main
  checkout is never touched.
- **Base branch** — which existing branch to branch from.
- **Task** — a short description; if an agent is attached, this is passed to
  it as its initial prompt.
- **Agent / Model** — pick from whichever agent CLIs DevDeck detected on
  your `$PATH` (see [Agent management](/docs/agent-management)). You can
  still spawn a worktree with none installed — it just falls back to a
  plain shell instead of launching an agent.

The new worktree shows up as a live card (running / waiting / error, with
token and diff stats once the agent starts working). Click it to open the
full terminal view — see [Working inside a
worktree](/docs/working-in-a-worktree).

## Root mode

Sometimes you just want a shell at the project root — no branch, no agent.
The same dialog has a **root mode** tab: it gives you a plain terminal
`cd`'d into the project's own path, shown with a house icon instead of a
branch icon. Deleting a root-mode worktree never touches git — there's
nothing to remove, since it's the project's own checkout.
```

- [ ] **Step 3: Write the working-in-a-worktree page**

Create `docs-site/content/docs/working-in-a-worktree.mdx`:

```mdx
---
title: Working inside a worktree
description: The tiling pane workspace, and everything you can put in it.
---

Opening a worktree switches the whole screen into a **tiling workspace**:
the top header disappears, the sidebar collapses to a narrow icon rail (back
arrow, workspace badge, nav icons — the only way back once the header's
gone), and the rest of the viewport becomes a canvas of resizable panes.

## Pane kinds

Every pane can hold one of four content kinds:

- **Terminal** — the real PTY the agent (or shell) is running in, backed by
  a live WebSocket. Navigate away and back and you reattach to the *same*
  running process — nothing restarts. A worktree always starts with one
  Terminal pane; splitting a Terminal pane spins up a genuinely independent
  second PTY, with its own shell/agent and no shared echo.
- **File explorer** — a tree of the worktree's files, with quick-open search
  (`Ctrl/Cmd-P`) and new-file/delete actions.
- **Editor** — click any file to open it in a CodeMirror tab. Every common
  language gets syntax highlighting; Go, TypeScript/JavaScript, Python, and
  Rust additionally get real language-server intelligence (autocomplete,
  inline diagnostics, go-to-definition) if `gopls` / `typescript-language-server`
  / `pyright-langserver` / `rust-analyzer` are on your `$PATH`. `Ctrl/Cmd-S`
  saves; `Ctrl/Cmd-W` closes the active file tab.
- **Git panel** — status, diff, stage/unstage/discard, commit, push, pull,
  scoped to this worktree's branch.

## Splitting and arranging panes

Each pane has a small header with its own tab strip (stack several tabs in
one pane without splitting), "split right"/"split down" buttons, and — when
the pane is focused — a "..." overflow menu. Drag a tab and drop it near a
pane's edge to split in that direction, or onto its center to merge it in as
another tab in that pane.

Your layout (which panes, which tabs, split sizes) is remembered per
worktree, so it reopens exactly as you left it.

<Callout title="On phones">
  Panes stack one full-bleed at a time instead of tiling side by side, and
  drag-and-drop is disabled.
</Callout>

## The overflow menu

On the focused pane, when its active tab is a Terminal, the "..." menu has:

- **Approve** — only shown while the worktree is waiting on you.
- **Open Git panel** / **Open file explorer** — add or focus that pane kind,
  since a fresh worktree starts with only a Terminal pane.
- **Details** — edit the worktree's branch, task, or model.
- **Delete** — removes both the database row and the on-disk `git worktree`
  (the agent process is stopped first).

## Document conversion

Two tools shell out to external CLIs on the server. If the underlying binary

The rest of the page is dev utilities that run entirely client-side: JWT
decode, Base64, URL encode/decode, hashing, JSON/XML/CSV formatting, UUID
generation, and timestamp conversion.

---
title: Deployment modes
description: Solo, hub + runtime machines, and the desktop app.
---

DevDeck is one binary (plus an optional native desktop shell around it),
run in different shapes depending on your situation.

## The one rule that applies to every mode: a project needs a Machine

Every project is executed by a registered **Machine** — git, worktrees,
terminals, and language servers all run there. You pick which one in the
**New project** dialog's machine dropdown. A brand-new hub starts with an
*empty* Machines registry, so that dropdown starts out empty too. Every mode
below is really just a different answer to "how does a Machine get into
that registry."

## Solo, one computer — `--role both`

The simplest correct setup for a single operator on a single computer: one
process handles the organizational data *and* the execution work, and
registers itself as a Machine on startup.

```bash
./devdeck-runtime-<platform> --role both --key <any-secret-string> --db devdeck.db
```

On startup it self-registers (marked local), so the **New project**
machine dropdown auto-selects it immediately. Everything else — routes,
auth, the UI — is identical to a plain hub.

## Hub + one or more runtime machines

Register a second machine when you want more CPU, a different OS, or a
machine physically closer to a particular repo to do the execution work.
All git/worktree/terminal/LSP activity for a project assigned to that
machine happens there; the hub only holds organizational data and federates
everything into one UI.

From the hub's **Machines** page → **Add Runtime**, there are two ways to
connect one:

- **Self-register command** — the dialog shows a ready-to-run command with
  a generated key and the hub's own URL already filled in. Run it on the
  target machine and it registers itself on startup.
- **Paste a connection string** — for a runtime that's already running,
  paste one `name|url|key` line. The hub verifies this immediately against
  the runtime's own API before creating the row, so a wrong key or an
  unreachable URL fails right away instead of silently registering a dead
  machine.

Either way, the machine shows up on the Machines page and becomes
selectable in **New project**. Hub and runtimes need to be on the same
Tailscale tailnet once they're on different machines.

### Signing in directly to a runtime

Every runtime process serves its own copy of the web UI at its own address,
and holds a read-only replica of its slice of the hub's catalog — so it
stays usable for its assigned projects even while the hub is down. You can
sign into a runtime's own UI two ways:

- **Paste the runtime's own key** — always works, including with the hub
  unreachable, since it only checks the key against this process.
- **"Sign in via hub"** — shown once the runtime has self-registered;
  mints a short-lived signed token on the hub (using your already-logged-in
  hub session) and redirects back to the runtime, signing you in without
  typing anything.

## Desktop app

DevDeck also ships as a native app (macOS/Windows/Linux). The first launch
asks how you want to run it — revisit the choice anytime from the app
menu's **Change Hub…** item.

- **Host locally on this device** — the app bundles the same Go backend as
  a background process, with its own local database — a complete,
  self-contained hub with nothing to configure. It registers itself
  automatically, exactly like `--role both` above, so **New project** works
  immediately.
- **Connect to a hub I already host** — for pointing the desktop app at a
  hub running elsewhere, you provide that hub's tailnet URL and its key.
  The window then behaves like a browser tab logged into that hub. In the
  background, if this device is on a Tailscale tailnet, the app also spawns
  its own bundled backend as a second, separate runtime process that
  self-registers with the hub you pointed it at — so your own computer
  shows up as a usable runtime on that hub within a few seconds, with
  nothing else to install or run.

<Callout title="No Tailscale on this device?">
  The background self-registration step just doesn't happen — browsing the
  hub is completely unaffected, but the app menu swaps **Change Hub…** for
  **⚠ Runtime not registered**; click it for the reason and the log path.
</Callout>

## Which one should I use?

| Situation | Use |
|---|---|
| Just you, one computer, simplest setup | `--role both`, or the desktop app's "Host locally" |
| You + a second/third machine for execution power | A hub + one or more runtime machines |
| You want a native app, and already host a hub elsewhere | Desktop app → "Connect to a hub" |
| You want a native app and nothing else running anywhere | Desktop app → "Host locally" |
```

---
title: Troubleshooting
description: Common issues and fixes.
---

- **A worktree opens to a plain shell instead of an agent.** The agent CLI
  you picked isn't on the server process's `$PATH`. Install it, or pick a
  different agent.
- **Tools page shows an error for a conversion.** The underlying conversion
  CLI isn't installed on the server — the error message includes the exact
  install command.
- **Lost your 2FA device.** Use one of the one-time backup codes shown at
  enrollment. If you don't have those either, there's no self-service
  recovery — it requires direct database access to clear the account's TOTP
  secret.
- **A registered machine shows offline.** The hub polls that machine's
  health endpoint with a short timeout — check the runtime process is
  actually running and reachable at the URL you registered it with, and
  that both machines are on the same tailnet if you're not on `127.0.0.1`.
- **New project's machine dropdown is empty.** A brand-new hub has no
  registered Machines yet — see [Deployment modes](/docs/deployment-modes).
  The fastest fix is running with `--role both`, or the desktop app's "Host
  locally" option, which registers itself automatically.
- **Pasting a connection string fails immediately.** The hub verifies the
  URL/key against the runtime's own API before registering it —
  "unreachable" means the URL isn't actually reachable from the hub, and a
  rejected key means it doesn't match that runtime's own key.
- **Desktop app shows "⚠ Runtime not registered" instead of "Change
  Hub…".** This device couldn't self-register as a runtime with the hub
  you connected to — click the menu item for the reason and log path. Most
  commonly, Tailscale isn't installed or this device isn't joined to a
  tailnet; browsing the hub itself is unaffected either way.
```
