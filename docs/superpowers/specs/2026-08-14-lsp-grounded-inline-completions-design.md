# LSP-Grounded AI Inline Completions with BYOK

## Overview

Copilot-style ghost-text inline completions in the Monaco code editor, generated by an LLM the operator brings their own API key for (Anthropic or an OpenAI-compatible endpoint), grounded against the file's real LSP data so the model is far less likely to suggest calls to functions that don't exist.

This is distinct from the LSP completion list DevDeck already has (`backend/internal/lsp`, `MonacoLspClient`) — that gives real, type-checked completions from gopls/tsserver but only single-symbol suggestions. This feature adds multi-token/multi-line AI-generated completions, using the LSP's own data as grounding input and as a post-generation check.

## Goals

- Ghost-text inline completions in the worktree code editor (`CodeFileEditor`), triggered on a typing pause, accepted with Tab.
- BYOK: the operator configures their own Anthropic or OpenAI-compatible API key in settings. No key configured = feature silently does nothing.
- Grounding: reduce hallucinated function/method calls by (a) feeding the model real LSP completion candidates and document symbols at the cursor, and (b) validating referenced calls in the model's response against the LSP before showing anything.
- Caching at three layers to control latency and cost.

## Non-goals

- Non-LSP-backed editors (SQL editor, env/skill editors, DocxView) — out of scope; no live LSP session exists there to ground against.
- Full agent-style multi-turn chat completions — this is single-shot, one request per trigger.
- Persisting completion history, telemetry, or analytics.
- True fill-in-the-middle (FIM) API support — current-generation Claude models return 400 on assistant-turn prefill, so this isn't available even if the provider is Anthropic. See "Prompt design" below for the workaround.

## Architecture — request flow

```
Monaco (CodeFileEditor)
  → InlineCompletionsProvider.provideInlineCompletions (debounced 300ms, cancels in-flight on new keystroke)
  → gather grounding: textDocument/completion + textDocument/documentSymbol over the file's EXISTING live LSP session (MonacoLspClient / lspSession.ts)
  → client-side cache check (suggestion-reuse; see Caching)
  → POST /api/completions/inline  { prefix, suffix, language, groundingSymbols }
       (hub-relative request — NOT machine-direct/proxy; see "Hub-only, worktree-agnostic" below)
  → hub: load BYOK config + key, hub-side cache check, call provider adapter (Anthropic or OpenAI-compatible)
  → { completion: string }
  → client-side post-validation: extract call-like identifiers from the completion text, check each against
    workspace/symbol over the same live LSP session; any unresolved identifier → drop the suggestion entirely
  → Monaco renders ghost text; Tab accepts (built into registerInlineCompletionsProvider)
```

### Hub-only, worktree-agnostic

The completions endpoint lives **only on the hub** (registered like `/api/auth/*`, gated on `!isRuntime` in `main.go`), regardless of which runtime machine the open worktree/file actually lives on. This works because everything the hub needs — prefix, suffix, and grounding symbols — is already sitting in the browser (Monaco's buffer + the file's live LSP session over `/ws/lsp`, which is itself already direct-or-proxied to the correct runtime by the existing `machineClient.ts` machinery). The hub never touches worktree data and never proxies to a runtime for this feature; it only holds the BYOK key and makes the outbound LLM call. The frontend must call this endpoint through the plain hub-relative `request()` in `frontend/src/lib/api.ts`, not `machineRequest`/`machineApi`.

This also means the key never has to leave the hub process — stronger than the "hub-owned key, hub-mediated proxy" framing originally proposed, since there's no runtime hop to secure at all.

## Backend: BYOK settings & storage

Same convention as `signin_pin_hash` / `PublishedSOCKSConfig`: kept off `domain.Settings` (never serialized by `GET /api/settings`) via dedicated store methods, single-row storage on the existing `settings` table (new columns).

```go
// backend/internal/domain/models.go — mirrors PublishedSOCKSConfig's placement
// CompletionsConfig is the BYOK configuration for AI inline completions.
// APIKey is deliberately excluded — see port.Store.CompletionsAPIKey().
type CompletionsConfig struct {
    Provider string `json:"provider"` // "anthropic" | "openai-compatible"
    BaseURL  string `json:"baseUrl"`  // openai-compatible only; empty = provider default
    Model    string `json:"model"`
    Enabled  bool   `json:"enabled"`
}
```

```go
// backend/internal/port/store.go
type CompletionsConfigPatch struct {
    Provider   *string
    BaseURL    *string
    HasBaseURL bool
    Model      *string
    Enabled    *bool
    APIKey     *string // nil = leave stored key unchanged; non-nil (incl. "") = replace
}

// Store interface additions:
CompletionsConfig() (domain.CompletionsConfig, error)                    // never includes the key
UpdateCompletionsConfig(p CompletionsConfigPatch) (domain.CompletionsConfig, error)
CompletionsConfigured() (bool, error)                                    // true iff a non-empty key is stored
CompletionsAPIKey() (string, error)                                      // "" if unset; used ONLY by the completions service, never by a handler response
```

New `settings` table columns: `completions_provider TEXT`, `completions_base_url TEXT`, `completions_model TEXT`, `completions_enabled BOOLEAN`, `completions_api_key TEXT`. Follow the existing migration pattern for adding columns to `settings` (same one used for `signin_pin_hash` / `socks_publish_*`).

Default provider/model when unset: `provider = "anthropic"`, `model = "claude-haiku-4-5"`, `enabled = false` (starts opt-in until a key is configured).

## Backend: completion endpoint

`POST /api/completions/inline`
```json
// request
{"prefix": "...", "suffix": "...", "language": "go", "groundingSymbols": [{"name": "Foo", "kind": "function", "detail": "func Foo(x int) string"}]}
// response 200
{"completion": "return fmt.Sprintf(\"%d\", x)"}
// response 204 — not configured, or disabled — frontend treats identically to "no suggestion"
```

`GET /api/completions/config` → `{"provider":"anthropic","baseUrl":"","model":"claude-haiku-4-5","enabled":false,"configured":false}` — `configured` reflects whether a key is stored; the key itself is never returned.

`PUT /api/completions/config` — body is a patch: any of `provider`, `baseUrl`, `model`, `enabled`, `apiKey` (all optional; omitted fields are left unchanged, matching the `Has*` convention in CONTRACTS.md for JSON-null-vs-absent). Returns the same shape as GET.

Both routes require normal hub auth (existing middleware) — no new auth mechanism.

## Backend: provider adapters

One interface, two adapters, in `backend/internal/completions/provider/` (parallel to, but not part of, `agentcore/provider` — this is a single stateless HTTP call, not an orchestrated agent session):

```go
type Adapter interface {
    Complete(ctx context.Context, req CompletionRequest, cfg domain.CompletionsConfig, apiKey string) (string, error)
}
type CompletionRequest struct {
    Prefix, Suffix, Language string
    GroundingSymbols         []GroundingSymbol
}
type GroundingSymbol struct{ Name, Kind, Detail string }
```

**No assistant-turn prefill** — current-generation Claude models (and this design should assume the same conservatism for arbitrary OpenAI-compatible endpoints) reject trailing-assistant-turn prefill with a 400. Both adapters instead send a normal user-turn instruction and **force a tool call** with a single-field schema (`{"completion": "<string>"}`), via `tool_choice: {"type": "tool", "name": "emit_completion"}` (Anthropic) / the equivalent forced `tool_choice` on Chat Completions (OpenAI-compatible). This guarantees a clean string with no prose, no markdown fences, and no parsing ambiguity — and is one uniform request shape across both providers.

**Anthropic adapter**: `model` defaults to `claude-haiku-4-5` (fast/cheap — this is a per-keystroke-latency feature, not a flagship-quality one; BYOK settings can still override to a different model). Mark the system prompt and the tool schema with `cache_control: {"type": "ephemeral"}` — those are static across every request; only `prefix`/`suffix`/`groundingSymbols` vary, so Anthropic's own prompt caching means steady-state requests only pay full price for the small dynamic part. See prompt-caching notes below on the 512-token minimum.

**OpenAI-compatible adapter**: `baseUrl` defaults to `https://api.openai.com/v1` when unset. Same forced-tool-call shape (Chat Completions `tools` + `tool_choice: {"type": "function", "function": {"name": "emit_completion"}}`). No caching code needed — OpenAI itself caches long-prefix requests automatically; self-hosted OpenAI-compatible servers that don't support caching simply see no speedup, not an error.

**Auth headers**: Anthropic uses `x-api-key: <key>` + `anthropic-version: 2023-06-01`, POST to `{baseUrl-or-default}/v1/messages`. OpenAI-compatible uses `Authorization: Bearer <key>`, POST to `{baseUrl}/chat/completions`. Both requests use a short client timeout (~15s) — this is a per-keystroke latency path, not a batch job; a slow provider should fail fast rather than hang the debounce queue.

## Backend: caching

Single in-memory bounded cache in the completions service (`backend/internal/service/completions.go`), not a separate package — no Redis, no persistence, single-operator local tool:

- Keyed on `sha256(prefix, suffix, groundingSymbols, provider, model)`.
- Max ~300 entries, 5-minute TTL, FIFO eviction on overflow (not true LRU — recency tracking isn't worth the complexity here; a bounded map with insertion-order eviction is enough to keep repeated/undo-redo lookups cheap).
- Cache lookup happens before the provider call; a hit skips the network entirely.

## Frontend: LSP grounding (client-side)

All LSP interaction for this feature reuses the file's **already-open** live session (`MonacoLspClient` via `lspSession.ts` — the same one hover/definition/completion already go through). No new backend LSP client.

**Before calling the backend** (context injection): issue `textDocument/completion` at the cursor position (top ~20 items, mapped to `{name, kind, detail}`) and `textDocument/documentSymbol` for the current file (capped ~50 symbols). These become `groundingSymbols` in the request. The `textDocument/completion` items are the strongest signal — they come straight from the language server's own type-checker, so grounding the LLM in "these are the real completions available here" is the primary anti-hallucination mechanism.

**After the backend responds** (post-validation): scan the returned completion text for call-like patterns (`\bidentifier\s*\(` and `\.identifier\s*\(`). For each, issue a `workspace/symbol` query for the bare name over the same live session. If any referenced call target doesn't resolve to a known workspace symbol, **drop the suggestion entirely** — fail closed, no attempt to edit/repair the text. Only the highest-risk, most-visible identifiers need checking for v1 (the first line of the completion is enough — deeper validation is future work, not required for this pass).

## Frontend: Monaco wiring

- `frontend/src/features/editor/inlineCompletions.ts` — implements Monaco's `InlineCompletionsProvider`: debounce (300ms after last keystroke) + cancel-in-flight (`AbortController`) on any new keystroke before the previous request resolves.
- Context window sent to the backend: prefix capped at ~100 lines / ~4000 chars before the cursor, suffix capped at ~50 lines / ~2000 chars after — bounds cost and latency; not user-configurable in v1.
- Wired into `CodeFileEditor.tsx`'s `onMount`, alongside the existing LSP wiring, and gated on the fetched completions config (`enabled && configured`) — if disabled/unconfigured, the provider is never registered, so there's zero overhead.
- Not registered on any other Monaco surface (`PlainCodeEditor`, `EnvSettingsEditor`, `SkillContentDialog`, DB SQL editor, etc.) — those have no live LSP session to ground against, matching the "LSP-backed code files only" decision.

## Frontend: client-side caching

- **Suggestion reuse**: before firing a new request, check whether the current prefix is exactly the previous request's prefix with more of the previously *shown* suggestion typed onto the end. If so, trim the cached suggestion to the unconsumed remainder and render it — no network call. This is what stops every keystroke *while accepting a suggestion* from re-hitting the LLM.
- **Document-symbol cache**: cache `textDocument/documentSymbol` results per `(uri, LSP document version)` — the LSP server already versions documents on every change — and only re-fetch when the version bumps, instead of on every debounce tick.

## Frontend: Settings UI

New "Completions" section in `frontend/src/features/overlays/DesktopSettingsDialog.tsx`, following the existing section pattern in that file (`SectionHeadRow` / `SettingsCard` / `InsetPanel`, same masked-reveal-copy treatment as the existing hub-key display): provider select (Anthropic / OpenAI-compatible), base URL field (shown only for OpenAI-compatible), model field (free text, pre-filled with the default), enabled toggle, and an API key input (write-only — never pre-filled with the real value; shows "configured"/"not configured" state instead, matching the BYOK-secret UX already established for the hub key).

Backed by a small React Query hook (`useCompletionsConfig`), not the global zustand store — this mirrors how `useVsCodeMode`/`useTailscaleStatus`/`useMachines` are already handled in this same dialog, and avoids touching `useDevDeckStore.ts`.

## Error handling / edge cases

| Case | Behavior |
|---|---|
| No key configured | `POST /api/completions/inline` → 204; frontend shows nothing, never surfaces an error to the user |
| `enabled: false` | Same as above — 204 |
| Provider HTTP error / timeout | Backend returns the standard `{"error":...}` envelope with an appropriate status (`handleStoreErr`-equivalent passthrough); frontend swallows it silently (a failed ghost-text suggestion is not worth interrupting typing with an error toast) |
| Post-validation drops the suggestion | No network error — this is expected behavior, not a failure; nothing renders |
| Non-LSP-backed file open in `CodeFileEditor` (LSP session never resolves, e.g. unsupported language) | Grounding symbols come back empty; request still fires with `groundingSymbols: []` — the model gets a weaker anti-hallucination signal but the feature still works, just without the resolve-check gate on post-validation (nothing to validate against, so nothing is ever dropped for that file — acceptable degradation, not blocked) |
| BYOK key rejected by provider (401) | Same as "provider HTTP error" — silent for now; visible only via the settings UI's `configured` flag not reflecting a working key (out of scope: proactive key validation on save) |

## Testing strategy

Backend: store CRUD tests (`store/completions_test.go`), service tests covering cache hit/miss and the disabled/unconfigured 204 path (`service/completions_test.go`), provider adapter tests against `httptest.Server` mocks asserting the forced-tool-call request shape and `cache_control` presence, handler tests for all three routes.

Frontend: `inlineCompletions.test.ts` unit tests for the suggestion-reuse cache logic, debounce/cancel behavior, and post-validation identifier extraction (LSP session and API client mocked) — this is where TDD earns its keep, since these are pure-ish functions with clear inputs/outputs. Settings UI gets a light render/interaction test in the existing `DesktopSettingsDialog`-adjacent style if one exists for that file; otherwise skip rather than force a test pattern that doesn't fit.

## Out of scope (explicitly deferred)

- Proactive API key validation on save (a test request to confirm the key works).
- Any editor surface beyond `CodeFileEditor`.
- True FIM/completions-endpoint support for self-hosted OpenAI-compatible servers that do support it (e.g. some vLLM/llama.cpp deployments) — the forced-tool-call approach works uniformly everywhere and is the v1 scope; a native-FIM fast path is a plausible future optimization, not required now.
- Deeper post-validation beyond first-line call-target resolution.
- Telemetry/usage tracking of completion accept/reject rates.
