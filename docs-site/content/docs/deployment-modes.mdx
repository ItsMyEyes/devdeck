title: Deployment modes
description: Solo, hub + runtime machines, and the desktop app.

DevDeck is one binary (plus an optional native desktop shell around it),
run in different shapes depending on your situation.

## The one rule that applies to every mode: a project needs a Machine

Every project is executed by a registered **Machine** — git, worktrees,
terminals, and language servers all run there. You pick which one in the
**New project** dialog's machine dropdown. A brand-new hub starts with an
*empty* Machines registry, so that dropdown starts out empty too. Every mode
below is really just a different answer to "how does a Machine get into
that registry."

## Solo, one computer — `--role both`

The simplest correct setup for a single operator on a single computer: one
process handles the organizational data *and* the execution work, and
registers itself as a Machine on startup.

```bash
./devdeck-runtime-<platform> --role both --key <any-secret-string> --db devdeck.db
```

On startup it self-registers (marked local), so the **New project**
machine dropdown auto-selects it immediately. Everything else — routes,
auth, the UI — is identical to a plain hub.

## Hub + one or more runtime machines

Register a second machine when you want more CPU, a different OS, or a
machine physically closer to a particular repo to do the execution work.
All git/worktree/terminal/LSP activity for a project assigned to that
machine happens there; the hub only holds organizational data and federates
everything into one UI.

From the hub's **Machines** page → **Add Runtime**, there are two ways to
connect one:

- **Self-register command** — the dialog shows a ready-to-run command with
  a generated key and the hub's own URL already filled in. Run it on the
  target machine and it registers itself on startup.
- **Paste a connection string** — for a runtime that's already running,
  paste one `name|url|key` line. The hub verifies this immediately against
  the runtime's own API before creating the row, so a wrong key or an
  unreachable URL fails right away instead of silently registering a dead
  machine.

Either way, the machine shows up on the Machines page and becomes
selectable in **New project**. Hub and runtimes need to be on the same
Tailscale tailnet once they're on different machines.

### Signing in directly to a runtime

Every runtime process serves its own copy of the web UI at its own address,
and holds a read-only replica of its slice of the hub's catalog — so it
stays usable for its assigned projects even while the hub is down. You can
sign into a runtime's own UI two ways:

- **Paste the runtime's own key** — always works, including with the hub
  unreachable, since it only checks the key against this process.
- **"Sign in via hub"** — shown once the runtime has self-registered;
  mints a short-lived signed token on the hub (using your already-logged-in
  hub session) and redirects back to the runtime, signing you in without
  typing anything.

## Desktop app

DevDeck also ships as a native app (macOS/Windows/Linux). The first launch
asks how you want to run it — revisit the choice anytime from the app
menu's **Change Hub…** item.

- **Host locally on this device** — the app bundles the same Go backend as
  a background process, with its own local database — a complete,
  self-contained hub with nothing to configure. It registers itself
  automatically, exactly like `--role both` above, so **New project** works
  immediately.
- **Connect to a hub I already host** — for pointing the desktop app at a
  hub running elsewhere, you provide that hub's tailnet URL and its key.
  The window then behaves like a browser tab logged into that hub. In the
  background, if this device is on a Tailscale tailnet, the app also spawns
  its own bundled backend as a second, separate runtime process that
  self-registers with the hub you pointed it at — so your own computer
  shows up as a usable runtime on that hub within a few seconds, with
  nothing else to install or run.

<Callout title="No Tailscale on this device?">
  The background self-registration step just doesn't happen — browsing the
  hub is completely unaffected, but the app menu swaps **Change Hub…** for
  **⚠ Runtime not registered**; click it for the reason and the log path.
</Callout>

## Which one should I use?

| Situation | Use |
|---|---|
| Just you, one computer, simplest setup | `--role both`, or the desktop app's "Host locally" |
| You + a second/third machine for execution power | A hub + one or more runtime machines |
| You want a native app, and already host a hub elsewhere | Desktop app → "Connect to a hub" |
| You want a native app and nothing else running anywhere | Desktop app → "Host locally" |
